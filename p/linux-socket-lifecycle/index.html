从头开始读tiny_web_server_rebuild的step1

我觉得我应该先把主线搞清楚,比如然后bind和connect会产生什么socket,也就是各个socket的生命周期,socket的数量和此刻各自在做什么我还不是很懂.

我们一步步来看,比如main一开始这里就是先创建listening_fd,此时没有任何东西,只是确定了这个socket走什么协议,

然后bind让这个socket绑定上某个端口,提前准备response的内容,同时满足也许是http的协议?也就是这个字符串为什么要硬编码一些body以外的东西,

这是为了让后续用户拿到之后知道怎么解析这个数据?然后while连接,如果accept失败,connetion_fd就会是负数然后一直循环,accept成果说明连接建立,

然后resv去拿到真实的请求数据.resv函数和send函数是需要这个connection_fd去执行吗?

所以会这样写::recv(connection_fd, request_buffer, sizeof(request_buffer), 0);send_all(connection_fd, response);

connnection_fd的socket对象负责程序逻辑和数据缓冲区(也许不对,总之是实际数据存储的地方)之间的连接?任何纠正和补充?

listen() 也不产生新 socket,只是让普通TCP socket变成监听socket

connect() 通常不会创建第二个 socket,这里也仅仅是操作而已

那服务器什么时候产生第二个 socket？->accept

因为一个服务器会有很多个连接,所以 fd 的作用之一就是：

告诉内核“我要操作哪一个 socket 对象”。

S1：永生的门卫
    socket → bind → listen
                │
                └── accept 新连接

    accept 得到
        ↓

        ↓
    send 响应
        ↓
    close


客户端：`socket → connect`  
服务器：`socket → bind → listen → accept`
时刻 Server sockets Client sockets 发生什么
server socket() 前 0 0 什么都没有
server socket() 后 1 0 S1
bind() 后 1 0 还是 S1
listen() 后 1 0 S1 成 listener
browser socket() 1 1 C1 出现
browser connect() 1 1 C1 开始连接
server accept() 后 2 1 S2 出现
HTTP 通信 2 1 C1 ↔ S2
server close(S2) 1 1→0 单次连接结束
server 继续运行 1 0 S1 继续监听
