Go 接口｜用统一方法描述不同结构体的行为

2025-10-07
阅读时长: 2 分钟
... 次阅读

两个测试的重复在哪里？

目前测试分别这样调用：

1
2

rectangle.Area()
circle.Area()

两个测试其实在执行同一种工作：

1
2
3
4
5

给定一个形状
    ↓
计算它的面积
    ↓
和预期值比较

如果以后添加三角形，比较代码还要重复一次。

我们希望写一个辅助函数：

1

checkArea(t, shape, want)

但问题出现了：

参数 shape 应该是什么类型？

写成 Rectangle，就不能传入 Circle。

写成 Circle，又不能传入 Rectangle。

我们真正需要知道什么？

这个辅助函数不关心宽、高、半径。

它只要求：

传进来的值拥有 Area() float64 方法。

于是可以定义：

1
2
3

type Shape interface {
	Area() float64
}

含义是：

1
2
3
4
5
6
7

Shape 要求
    │
    └── Area() float64
             ↑
             │
        Rectangle 具有这个方法
        Circle    具有这个方法

所以两种类型都能作为 Shape 使用。

为什么没有 implements？

Go 的接口满足关系是隐式的。

你不需要写：

1

Rectangle implements Shape

编译器会检查方法集合是否满足接口要求。

因此：

  • Rectangle 满足 Shape。
  • Circle 满足 Shape。
  • int 不满足 Shape，因为它没有 Area() 方法。

接口不是把两种结构体的数据合并起来。

它只是声明使用者需要哪些操作。

解耦体现在哪里？

原来辅助函数需要具体类型。

现在：

1

checkArea(t, shape Shape, want float64)

它只知道：

1

got := shape.Area()

不知道 shape 内部存储的是 Width，还是 Radius。

调用时：

1
2

Rectangle → Shape → 调用 Rectangle.Area
Circle    → Shape → 调用 Circle.Area

运行时，接口值包含动态类型与具体值的信息，因此能够调用到对应的实现。

但什么类型可以传入接口，是编译器在编译时检查的。

这就是接口带来的解耦：调用方依赖需要的行为，而不是所有具体实现细节。

t.Helper() 解决什么？

我们把比较逻辑放进 checkArea 后，测试失败会经过这个辅助函数。

如果错误总是定位到辅助函数内部，排查起来并不方便。

所以调用：

1

t.Helper()

告诉 Go 测试框架：

这个函数是测试辅助函数，报告错误时应尽量指出调用它的位置，而不是只指出辅助函数内部的位置。

它不会改变测试是否通过。
