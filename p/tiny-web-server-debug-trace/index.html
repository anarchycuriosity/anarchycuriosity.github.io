从函数出口反推决策点

我感觉我一般都是对着 return 附近的位置，视线拉远一些，看看是不是在某个逻辑模块内，打 debug_trace。

你觉得这个思路对吗？因为 return 往往对应某种状态的改变？

这个直觉是有道理的，但需要区分两个概念：

  • return：控制流的出口，代表当前函数的一条执行路径结束。
  • 状态变化：对象内部数据发生改变，例如 state、scan_offset、content_length 被更新。

二者可能同时发生，但并不等价。

它的价值在于：不需要从函数第一行开始盲目寻找打点位置，而是先找到可能具有诊断意义的执行路径。

区分解析结果和对象状态

这里需要修正：

return 只能证明本次函数调用结束，不能证明对象的内部状态发生改变。

以 HTTP Parser 为例。

假设收到：

GET / HTTP/1.1\r

由于尚未收到 \n，解析器无法确认请求行结束。

       ↓

等待下一批数据

此时：

观察对象 实际含义
parse_result need_data，本次解析暂时无法继续
state 可能仍保持原来的解析阶段
scan_offset 记录已经扫描的位置
reason none，因为等待数据不是解析失败
Parser 对象 仍然存在，保留进度供下次调用使用

这里涉及三个不同层面的事情：

  1. 函数调用结束了。
  2. 某些进度字段可能更新了。
  3. 解析器的逻辑状态未必改变。

特别需要注意：返回值不等于对象状态。

例如 need_data 是本次 parse() 的执行结果，不一定是持久保存在 Parser 内部的一个状态。

用日志还原控制流与状态变化

我最初是从 return 附近拉远视野，判断这个位置是否处于某个有意义的逻辑模块。

现在看来，这实际上是一种从函数出口逆向寻找决策原因的方法。

需要保留这个直觉，但不能把 return 直接理解成状态变化。

更加准确的模型是：

return 帮助我定位执行结果，分支判断帮助我解释结果原因，成员变量变化帮助我重建状态演化。

对于 TinyWebServer 的 HTTP Parser：

  • 观察 return，理解本次调用如何结束。
  • 观察 break / continue，理解控制流如何推进或暂停。
  • 观察 state 和 scan_offset 等字段，理解解析器如何保存进度。
  • 观察 debug_trace，验证自己推测的因果链。

最终衡量打点质量的标准不是：

我是不是在每个重要 return 前都打了日志？

而是：

当解析器得到一个异常或不符合预期的结果时，我能否仅凭日志还原它为什么走到这里，以及下一次调用会从哪里继续？

这也对应着源码阅读中的三个层次：

1
2
3
4

控制流：程序走了哪条路径？
    ↓
数据流：哪些成员变量发生了变化？
    ↓
因果链：什么输入和判断导致了这些变化？

最终结论：打点位置应当围绕有诊断价值的决策和状态变化来选择，而 return 是寻找这些位置的一个很好的起点，不是唯一的判断依据。
