应该由谁提供联盟数据？

PlayerServer 应该负责 HTTP 协议：

  • 匹配端点。
  • 获取请求参数。
  • 调用数据操作。
  • 生成 HTTP 响应。

而 PlayerStore 负责数据：

  • 查询玩家胜场。
  • 记录玩家获胜。
  • 返回玩家清单。

因此给 PlayerStore 增加 GetLeague() []Player。

为什么新增接口方法会引发编译错误？

假设原来的 PlayerStore 只有两项要求：

GetPlayerScore 和 RecordWin。

现在接口增加 GetLeague。

那么传给 NewPlayerServer 的所有具体 Store 类型，都必须提供这个方法。

如果只修改接口，不修改 InMemoryPlayerStore，编译器会提示类似：

1
2

*InMemoryPlayerStore does not implement PlayerStore
(missing method GetLeague)

这是 Go 隐式接口实现机制在发挥作用。

不需要写 implements PlayerStore，但必须具备接口所要求的完整方法集。

Store 作用
StubPlayerStore 测试中提供事先准备好的数据
InMemoryPlayerStore 实际运行时保存胜场

先让测试里的 Stub 返回指定联盟数据。

Content-Type 为什么必须先设置？

上一篇直接把 JSON 写入 HTTP 响应体，却没有明确声明数据格式。

需要增加：

Content-Type: application/json

但设置响应头与写入响应体有执行顺序。

Header().Set(...)
       │
       ▼
第一次 Write / Encode
       │
       ▼
状态码与响应头被提交
       │
       ▼
响应体继续写入

如果响应已经提交，再设置普通响应头，就不能改变已经发送出去的头部。

原章曾在 json.Encoder.Encode 后面调用 WriteHeader(200)。这种顺序不正确，因为编码器可能已经触发了隐式的 200 状态码提交。

正确方式是：

  1. 先设置 Content-Type。
  2. 需要非默认状态码时，先调用 WriteHeader。
  3. 最后编码 JSON。

本例返回默认 200，因此不需要额外调用 WriteHeader(200)。

此外，Encode 可能返回错误。响应一旦部分写出，就不能简单通过之后调用 WriteHeader(500) 来修复。当前课程只记录编码错误，真正的流式输出失败处理可以留到后续工程实践。
