真正执行 Feed 业务逻辑的是另一个程序。

这意味着远程调用还可能遇到本地函数通常不涉及的问题，例如：

  • 对方程序没有运行。
  • 网络不可达。
  • 请求传递失败。
  • 等待结果超时。

因此，RPC 并不是让远程程序真的变成了同一个进程中的普通函数。

它只是提供了一种组织远程调用的编程模型，并由相应框架处理部分通信工作。

那么为什么还要使用 RPC 框架？

一个可能的工程收益是：让跨程序调用更接近约定好的方法接口。

例如 API 希望调用：

1

Feed(请求参数) → 返回结果

借助框架，可以统一组织调用接口、参数传递、结果处理及部分远程调用相关机制。

但引入框架也有成本：

  • 需要理解框架的调用机制。
  • 需要维护服务之间的接口约定。
  • 会增加依赖、配置和调试复杂度。

因此，这是一种工程取舍。

Kitex 在调用链上的位置

注意，Kitex 不负责所有网络通信：

  • 手机 → API：Hertz 处理 HTTP。

  • API → Video：Kitex 处理 RPC。

  • Video → MySQL：数据库驱动处理。

  • Video → MinIO：MinIO SDK 处理。
