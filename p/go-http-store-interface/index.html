Go net/http｜PlayerStore 接口与 Handler 的存储依赖

2026-10-20
阅读时长: 3 分钟
... 次阅读

现在的问题出在哪里？

上一版：

1
2
3
4
5
6
7

HTTP 请求
    ↓
PlayerServer
    ↓
GetPlayerScore
    ↓
硬编码 Pepper=20、Floyd=10

假设以后分数存储在 MySQL 中。

直观做法是在 PlayerServer 中直接连接数据库。

但这样会导致一个问题：

只想测试 HTTP Handler 是否正确返回数据，也必须先准备数据库。

实际上，我们希望：

1
2
3
4
5
6
7

                  PlayerStore 接口
                         ↑
                PlayerServer 依赖它
                         |
             +-----------+-----------+
             |                       |
        测试用 Stub             真实数据存储

Handler 不需要知道存储的具体类型，只需要知道对方具有 GetPlayerScore 方法。

从函数提取自然走向接口

先定义：

1
2
3

type PlayerStore interface {
	GetPlayerScore(name string) int
}

它描述了一种能力：输入玩家名，取得整数分数。

再让结构体保存依赖：

1
2
3

type PlayerServer struct {
	store PlayerStore
}

为什么这次要使用结构体，而不是最初的普通函数？

因为 PlayerServer 现在需要保存一个状态：它持有哪个存储实现。

这里的状态是依赖引用，不是请求过程中变化的分数。

请求执行时：

1
2
3
4
5

server (*PlayerServer)
    |
    +-- store (PlayerStore 接口值)
              |
              +-- 指向具体的 StubPlayerStore

调用 p.store.GetPlayerScore(name)，Go 会根据接口中实际保存的具体类型调用相应方法。

无需写 Java 风格的显式 implements 声明。

谁来实现 ServeHTTP？

最初使用普通函数：

1

PlayerServer(w, r)

现在 PlayerServer 已经变成结构体类型，不能再当作函数调用。

给它实现方法：

1
2
3
4

func (p *PlayerServer) ServeHTTP(
	w http.ResponseWriter,
	r *http.Request,
)

这样 *PlayerServer 就满足 http.Handler 接口。

main 可以直接把服务器对象传入 ListenAndServe，不再需要 http.HandlerFunc。

注意：因为方法接收者是 *PlayerServer，我们使用指针来满足接口，而不是结构体值。

GET 和 POST 的职责不同

已经实现的 GET：

1
2
3
4
5

GET /players/Pepper
        ↓
store.GetPlayerScore("Pepper")
        ↓
返回分数

现在需要 POST：

1
2
3
4
5

POST /players/Pepper
        ↓
store.RecordWin("Pepper")
        ↓
返回 HTTP 202

服务器开始有两种行为：

  • GET：读取状态。
  • POST：修改状态。

因此 ServeHTTP 需要根据 r.Method 选择处理路径。

原章首先写一个最简单的 POST 分支，只返回 202 Accepted。

这能让状态码测试通过，但还不能证明真的记录了胜场。

只检查 202 会遗漏什么？

考虑：

1
2
3
4

if r.Method == http.MethodPost {
	w.WriteHeader(http.StatusAccepted)
	return
}

客户端看到了 202。

可是 RecordWin 一次都没有调用。

如果测试只检查状态码，它就无法发现这个问题。

我们需要观察 Handler 是否正确调用了存储层。

这里引入 Spy。

Spy 与 Stub 的区别是什么？

前一篇的 Stub：

1
2
3

测试要求 GetPlayerScore("Pepper")
             ↓
Stub 返回预设的 20

它提供可控的返回值。

现在的 Spy：

1
2
3
4
5
6
7

PlayerServer
     ↓
RecordWin("Pepper")
     ↓
Spy 把 "Pepper" 放进 winCalls
     ↓
测试检查 winCalls

Spy 不必实现真正的胜场累加。

它只记录外部调用了什么，以便测试交互行为。

本篇让 StubPlayerStore 同时承担 Stub 和 Spy 两种角色：

1
2
3
4

type StubPlayerStore struct {
	scores   map[string]int
	winCalls []string
}

为什么先检查调用次数，再检查名字？

第一步，只检查：

1

len(store.winCalls) == 1

我们可能写出一个故意不完整的实现：

1

p.store.RecordWin("Bob")

调用次数正确，测试通过。

但显然记录错了玩家。

第二步，再增加：

1

store.winCalls[0] == "Pepper"

此时错误暴露出来：

1

got "Bob", want "Pepper"

然后 Handler 从 URL 中取得真正的玩家名：

1

p.store.RecordWin(player)

这里还有一个小边界：

在读取 winCalls[0] 之前，先检查切片长度。

如果调用次数错误，应使用 t.Fatalf 立即结束当前测试，避免索引越界。
