注册路由与请求校验

拿 alice 注册这一次请求当主线。请求方法是 POST，地址是 /douyin/user/register/?username=alice&password=p。

S01 的 Hertz 收得到请求，但路由里没有对应的处理函数，所以返回 404。S02 登记 POST /douyin/user/register/ 后，同一条请求终于进了注册 handler。进了 handler 以后，第一件事是弄清客户端把两个值放在哪儿。

原版通过 c.Query("username") 和 c.Query("password") 从 URL 的 ? 后面取参数。POST 决定这条请求匹配哪个 handler，c.Query 决定 handler 到哪儿取值。把 username 和 password 只放进 JSON 正文，这条请求仍能匹配路由，但 c.Query 会读到空字符串，handler 返回 400。 原版路由 · 原版 Register

接下来只改一个值试着推演。alice 和 p 都通过校验。删掉 password，handler 会写 400。把用户名换成 11 个 中，每个 中 在 UTF-8 中占 3 字节，len(username) 就是 33。原版与 show 都会走长度超限分支，HTTP 返回 200，JSON 里的 status_code 是 -1。show 把提示改成了「32 字节」，与实际检查一致。 show 参数校验

回到源码看每个校验分支末尾的 return。c.JSON(...) 把状态码和 JSON 写进当前请求的响应对象，所以 handler 的签名里可以没有返回值。下一行 return 结束这个函数。少了它，校验失败的请求还会继续往下走，后续分支就可能再写一次响应，或者把无效输入交给后端。

动手 · 先写出请求到校验这一段

在现有 internal/api 里新增 register.go。先读附录中 RegisterUserRoute 的前半段，然后写出下面这条顺序：

登记 POST → 用 c.Query 取两个字符串 → 空值写 400 并结束 → 超过 32 字节写 200 / -1 并结束

RegisterResult 是交给 c.JSON 的响应数据。先写好 StatusCode 和 StatusMsg，看它们怎样用 JSON tag 变成 status_code 与 status_msg。合法请求接下来要调用谁，下一节再接上。

查阅指引。 在 Hertz v0.5.2 源码里看 POST 的签名，确认第二个参数为何能传一个函数。再在 RequestContext 里找 Query 和 JSON，分别确认前者返回字符串，后者写入响应。 Hertz v0.5.2 RouterGroup.POST 所在文件 · RequestContext 源码 · JSON

Handler 与注册函数的接缝

HTTP handler 此时拿到了 alice 和 p。它能判断这两个字符串是否符合接口要求。至于 alice 是否已被注册、该写入哪张表、成功后返回哪个用户 ID，这些要由用户服务处理。

原版在这个交接点把用户名和密码装进 UserRegisterRequest，交给 rpc.Register。后者调用 Kitex 的 userClient.Register，用户服务才去查库、写库并签发 token。S02 正在复刻的是箭头左边的 HTTP 处理和中间的交接位置。 原版 HTTP handler · 原版 RPC 调用 · 原版用户服务

Hertz 注册 handler → RegisterFunc 接入点 → Kitex 用户服务 → MySQL

show 用 type RegisterFunc func(context.Context, string, string) (RegisterResult, error) 给一种函数签名起了名字。读到这里，先把它看成一份约定：调用方给出执行用的 ctx、用户名和密码，被调用的函数交回注册结果或调用错误。

再看 RegisterUserRoute(hz, register)。登记路由时，register 作为一个函数值传进来。传给 hz.POST 的匿名 handler 会记住它，等 alice 发来请求并通过检查时，才执行 register(ctx, username, password)。这里发生了两次交接：启动时交给 handler 一个可调用的函数，请求到达后再把参数交给那个函数。 show RegisterFunc 与调用处

真实进程在 RegisterRoutes 中传的是 nil。这表示路由已装好，但后端函数还没有接上。所以 alice 通过校验之后得到 503 和 status_code: -1。去掉 register == nil 的检查，合法请求就会尝试调用一个空函数值，触发 panic。这个检查让「本步停在哪里」变成客户端看得见的响应。 实际装配入口

动手 · 接上函数参数，让真实路由走到 503

在 register.go 把 RegisterFunc、空函数检查和调用路径接到上一节的校验后面。在 learner 已有的 RegisterRoutes 里只加 RegisterUserRoute(hz, nil)。保留原有 /healthz、服务构造和测试。两个 .go 文件同属 package api，可以直接调用同包函数，无须把 register.go 写进 import。每个文件仍各自导入它用到的包。

查阅指引。 想确认这次改动接到了真正的服务器上，就顺着 show 的 NewServer → RegisterRoutes → RegisterUserRoute 走一遍。看到最后一跳的 nil，就能解释为什么真实请求停在 503。 show 服务器装配

错误与结果的双重检查

现在保持 alice / p 不变，只在测试里给 RegisterUserRoute 传一个普通 Go 函数。这样可以观察同一个 HTTP handler 如何处理不同的后端结果：

函数交回什么 handler 写回什么
err != nil，例如调用失败 HTTP 502、status_code: -1，响应使用固定消息
err == nil，业务结果说「用户名已存在」 HTTP 200、非零 status_code，失败响应省略用户 ID 和 token
err == nil，业务结果返回用户 ID 42 和测试 token HTTP 200、status_code: 0，把测试结果写进 JSON

试着把前两种放回同一个请求里想。用户服务如果明确说「用户名已存在」，handler 已经拿到一个业务答案。调用过程中如果出了错，handler 没有拿到可用的业务答案。原版用 res, _ := rpc.Register(...) 丢掉了调用错误，紧接着读取 res.StatusCode。如果这次调用失败并返回 nil 响应，继续访问字段就会 panic。show 按顺序先检查 err，再读 result.StatusCode。 原版 RPC 结果读取 · show 响应分支

读 c.JSON(http.StatusOK, result) 时，第一项是 HTTP 状态，第二项才会被编码成 JSON。客户端看到 200 后还要读 status_code，因为长度超限、业务拒绝和业务成功都可能用 HTTP 200。业务失败时，show 先把 UserID 和 Token 清零，再由 JSON tag 里的 omitempty 省略这两个字段。原版响应类型没有这两个 omitempty，所以这一步保留了原版查询参数和校验规则，调整了失败响应的字段形状。 show 响应类型 · 原版响应类型

动手 · 用替身把每个出口跑出来

在 internal/api 新增 register_test.go。每个测试创建一个 Hertz 实例，用 RegisterUserRoute(hz, backend) 装配该场景的函数，再用 ut.PerformRequest 发 POST。先试合法输入加 nil，确认得到 503。再给同一输入换两个替身，分别返回一个 error 和一个业务拒绝，观察 502 与 200 / -1。最后补上缺参、长度超限和成功映射。

把「缺参」再单独跑一遍，传入一个只要被调用就让测试失败的替身。这样能验证请求在校验处结束，后端函数没有收到无效参数。附录中的 42 和 test-token 只来自测试函数，用来验证 HTTP 映射。

查阅指引。 查 Hertz v0.5.2 的 ut.PerformRequest 时，顺到 engine.ServeHTTP(...) 就够了。它把构造好的请求交给 hz.Engine，所以即使没有 cmd/api/main.go，也能观察响应。测试用 url.Values.Encode() 生成查询串，中文用户名也走正常 URL 编码和解析。 Hertz v0.5.2 PerformRequest · show 替身测试
