Go 文件存储｜空文件、损坏数据与失败后的缓存一致性

2026-10-20
阅读时长: 2 分钟
... 次阅读

为什么之前一直没有发现初始化错误？

我们在构造函数中写过：

1

league, _ := NewLeague(file)

下划线直接忽略了错误。

对于空文件，JSON 解码器会返回 EOF。

但空文件和损坏文件并不应该采用相同处理方式。

文件内容 应该怎么处理
空文件，长度为 0 初始化为空数组 []
合法 JSON 数组 正常解码
not JSON 返回解析错误
文件读取失败 返回读取错误
写入失败 返回错误，HTTP 不应报告 202

怎样判断文件真的为空？

使用 file.Stat() 获取文件信息，再调用 Size()。

1
2
3
4
5
6
7

Stat
  ↓
Size == 0 ?
  ├── 是：写入 [] → Seek(0)
  └── 否：Seek(0)
  ↓
NewLeague

必须在写入 [] 后再次 Seek。

否则位置停在 [] 的末尾，随后的解码仍会遇到 EOF。

为什么构造函数应该返回 error？

文件持久化的初始化可能失败：

1
2
3
4
5
6
7

main
  ↓
OpenFile
  ↓
NewFileSystemPlayerStore
  ├── 初始化成功 → 启动 HTTP
  └── 初始化失败 → 返回 error → 终止启动

因此构造函数改为：

NewFileSystemPlayerStore(file) (*FileSystemPlayerStore, error)

这里使用 %w 包装错误：

1
2
3
4
5

load league from game.db.json
    ↓
parse league JSON
    ↓
invalid character ...

调用者能看到错误发生在什么阶段，也可以使用 errors.Is 或 errors.As 检查底层错误。

写入失败时，为什么不能先修改缓存？

旧流程：

1
2
3
4
5
6

league.Wins++
   ↓
写入文件失败
   ↓
内存 = 4
文件 = 3

两个状态发生分歧。

改为：

1
2
3
4
5
6
7

复制 league → updated
     ↓
修改 updated
     ↓
写入成功？
  ├── 是：f.league = updated
  └── 否：返回 error，缓存不提交

这样至少可以避免普通写入失败后错误地提交内存缓存。

但注意：这仍然不是完整事务。tape 可能已经截断或部分写入文件；真正的磁盘原子性不在本章范围内。

为了让 HTTP 端知道失败，PlayerStore.RecordWin 现在返回 error。

发生错误时返回 500，而不是 202。
