排序放在 HTTP 层还是存储层？

产品负责人要求：

GET /league

返回按胜场从高到低排列的玩家。

可以选择：

1
2
3
4
5

方案 A：
PlayerStore → PlayerServer 排序 → HTTP

方案 B：
PlayerStore 排序 → PlayerServer → HTTP

原书选择方案 B。

原因是排序本质上属于数据查询结果的组织方式。

假设以后换成 SQL 数据库，可以在存储层使用 ORDER BY，而 HTTP 层无需改变。

我们也保持这一设计。

sort.Slice 如何工作？

sort.Slice 接收切片，以及一个比较函数。

比较函数回答：

“下标 i 的元素是否应该排在下标 j 的元素之前？”

按 Wins 降序：

1
2
3
4

Chris: 33
Cleo:  10

33 > 10 → Chris 在前

但还有一个细节。

如果 Ada 和 Chris 都是 2 胜，原书没有规定谁在前面。

为了测试稳定且结果可预测，我们增加一个规则：

  • 首先按 Wins 降序。
  • Wins 相同，按 Name 字典序升序。

这不是 sort.Slice 自动保证的，而是我们明确写出的业务规则。

为什么不能直接排序缓存？

sort.Slice 会原地修改传入切片的元素顺序。

如果直接排序 f.league：

1
2
3
4
5

共享底层数组
     ↓
GetLeague 排序
     ↓
内部缓存的顺序也改变

这里选择：

1
2
3
4
5
6
7

f.league
   ↓
复制 snapshot
   ↓
sort.Slice(snapshot)
   ↓
返回 snapshot

这样 HTTP 获得排序结果，但不改变持久化存储的内部列表顺序。

Chris → POST 两次
Ada   → POST 两次

重启服务后访问 /league。

  {"Name":"Ada","Wins":2},
  {"Name":"Chris","Wins":2},
  {"Name":"Cleo","Wins":1}

这同时验证：

  1. POST 写入数据。
  2. 数据跨重启仍然存在。
  3. GET 返回正确 JSON。
  4. 玩家按胜场排序。
  5. 相同胜场有确定顺序。
