Go微服务的重要概念->代码生成

Kitex 明明是一个通用框架，为什么它竟然知道我的业务叫 VideoService，甚至知道里面有 Feed 方法？

Kitex 不是专门处理 HTTP 的框架。 这个项目使用 Hertz 处理 HTTP，Kitex 处理服务之间的 RPC 通信。Request 和 Response 则是两种通信都可能使用的概念。

注意一个细节,有些地方的kitex不是指通用的kitex框架包而是文件中给自己项目生成的代码包取的命名.

kitex "github.com/bytedance-youthcamp-jbzx/tiktok/kitex/kitex_gen/video"

我现在对于handler,rpc,还有kitex生成源码,他们背后的业务和关系还是很模糊

我们先从用户的角度来看,这个项目不是一个程序包办所有服务的 API进程专门用来接待app发来的http请求,video进程负责执行视频的相关业务,比如查数据库. 当用户发送请求的时候,请求首先抵达API进程,但是真正查询视频列表的代码在video进程里面.问题来了,api进程怎样让另一个独立进程进行查询?它不能像调用自己进程的一个普通函数那样直接跳到另一个进程的函数内部执行

我们首先看注册这个

为什么明明是videoservice调用了NewClient但是video进程不是客户端?虽然我看过项目架构我知道它不是客户端而是服务端,但是为什么函数是这样的? 关键偏差是,videoservice是go的包名,而不代表正在执行代码的video进程.实际上你看它的文件所在位置就可以知道,它其实是由api进程执行的. 同一个videoservice包,同时提供了NewClient和NewServer,因为这是kitex根据.proto生成的代码包,要同时提供客户端和服务端所需的代码

videoservice包其实是kitex为双端提供的契约和动作

好吧那么kitex提供了一个代码包来为两端服务,可是这个代码包是怎么来的?也就是说只要我通过proto提供接口和协议,这样我就只用写一端的逻辑,另一端的逻辑由kitex负责?可是为什么我在video里面看到的videoservice全都是kitex产生的代码包,这感觉像是凭空产生,可是这要如何跟我们的业务对接? kitex生成了什么?我们需要写什么?Kitex 自动生成的是两端的通信代码，而不是自动实现一端的业务逻辑。

第 1 步：开发者编写 video.proto

定义 FeedRequest、FeedResponse 和 VideoService 的 RPC 接口。

运行 kitex 代码生成命令

第 2 步：Kitex 生成 Go 源码

生成消息类型、RPC 接口、客户端代理、服务端分发代码等。

开发者编写业务实现

第 3 步：实现 VideoServiceImpl

自己编写数据库查询、视频发布、MinIO 访问等业务。

第 4 步：编译并运行 API 和 Video 进程

两端使用生成的 Go 代码完成 RPC 通信。

具体的实现就是到了video微服务的文件夹了

kitex生成的代码并不是替代我们写的业务的关系,而是在需要rpc通信的时候执行那个部分的源码.也就说实际的数据流差不多是,api进程在handler解析http参数,然后rpc的feed函数调用了videoservice,那么api进程就会通过kitex生成的代码来向video进程通信,跨进程.
