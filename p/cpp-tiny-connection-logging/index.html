已经有 fd，为什么还需要 connection_id？

原注释：

我不是很理解这个 id 是干什么的。

它们承担不同职责。

fd 是内核分配给进程的文件描述符，用来操作已接受的 socket。

connection_id 是当前程序自己递增的连接编号，用于区分连接历史。

例如：

连接 connection_id fd
A 建立 1 4
A 关闭 1 4
B 建立 2 4
B 关闭 2 4

数字只是示例。

重点是：关闭后的 fd 数值可能被复用。

如果日志只记录 fd=4，历史上的两个连接可能看起来像同一个连接。

增加 connection_id 后：

1
2

connection_id=1 fd=4
connection_id=2 fd=4

就能区分它们。

在当前程序中，connection_id 只是诊断标识，不是新的 socket，也不是 HTTP 请求编号。

为什么 connection_id 用 %zu，fd 用 %d？

原注释：

因为 fd 如果是 -1 就代表连接失败吗？它承接了一部分信息。

fd 使用 %d 的直接原因是它的类型为 int。

返回 -1 表示失败是相关背景，但不是选择占位符的唯一依据。

格式化输出要求占位符与实际传入的参数类型匹配。

数据 类型 格式
connection_id std::size_t %zu
connection_fd int %d
received_bytes ssize_t %zd
diagnostic_reason() const char* %s

%zu 用于 size_t，%zd 对应其有符号形式。

parse_result 是枚举类型。当前代码先使用 static_cast<int> 转成整数，再通过 %d 输出。

这种做法可以打印枚举编号，但不能自动显示有意义的枚举名称。

为什么 debug_trace 使用 va_list？

普通 fprintf 可以直接接收格式字符串和后续参数。

但 debug_trace 自己也是一个接收可变参数的函数，需要把这些参数转交给 vfprintf。

    ├── component

          ↓
       va_start
          ↓

          ↓
       vfprintf

va_start(arguments, format) 使用最后一个固定形参 format 来初始化可变参数访问状态。

format 本身不是保存所有参数的数组。

vfprintf 根据格式字符串中的占位符读取 va_list 中的参数。

这类格式化接口对类型匹配和指针有效性都有要求。

例如，%s 需要有效的 C 字符串指针，这正是未初始化 last_failure_reason 特别危险的原因。
