一个已经不需要结果的请求

在Go的服务端开发中,一个请求往往需要经过许多函数,但这些函数需要知道:这个请求是否还值得继续执行. 比如我们来看feed请求链

假如用户在请求完成中途就关闭了界面,那么数据库怎么知道用户不需要结果了? 如果不使用取消机制,那么有大量这样的请求的时候,服务端就可能白白占用大量链接CPU和内存. 从http开始,context就像是一个随着请求流动的控制凭证. context本身并不具备取消的功能,要看函数或者它调用的库是否主动响应取消信号

type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
方法 解决的问题
Deadline() 最晚什么时候必须结束？
Done() 有没有收到取消通知？
Err() 为什么结束？取消还是超时？
Value() 有没有随调用链传递的信息？
其中最值得理解的是 Done()。

它返回一个 channel。

当context被取消的时候,这个channel会被关闭

func doWork(ctx context.Context) error {
    select {
    case <-ctx.Done():
        return ctx.Err()
    case <-time.After(3 * time.Second):
        return nil
    }
}

取消与错误返回的顺序

取消信号并不是沿着 API → Service → DB 一层层发送过去的。

真正发生的是：

  1. 各层函数提前拿到了同一个 Context。

  2. 一个 goroutine 调用 cancel()，改变 Context 内部的状态并关闭通知 channel。

  3. 另一个 goroutine 正在等待这个 channel，发现它关闭后，主动 return。

  4. 随后错误才沿函数调用栈逐层返回。

func API(ctx context.Context) error {
    return Service(ctx)
}

func Service(ctx context.Context) error {
    return QueryDB(ctx)
}

func QueryDB(ctx context.Context) error {
    <-ctx.Done()
    return ctx.Err()
}
