生成代码的字段契约

在 internal/user_rpc/register.go 的返回结构体里，把 UserID: response.UserID 改成 UserID: response.UserId。

response 指向生成的 user.UserRegisterResponse，它声明的是 UserId。冒号左边在给手写的 api.RegisterResult 填字段，那里声明的是 UserID。例如 RPC 给了 UserId = 42，适配器就把 42 放进 API 结果的 UserID，之后 HTTP 层通过 JSON tag 把它写成 user_id。从生成文件里查字段名即可，修改落在手写适配器。 生成的响应类型

1

"$s04_go" test -tags stdjson -count=1 -v ./internal/user_rpc -run '^TestRegisterMapsResponse$'

检查点 测试通过，42 正确搬到了 API 结果。但日志还会冒出 register response missing。明明有响应却打印「缺失」，先记下这个现象，下一轮先处理会崩溃的路径。

错误返回后的控制流

先单独跑调用失败测试。

1

"$s04_go" test -tags stdjson -count=1 ./internal/user_rpc -run '^TestRegisterReportsCallFailure$'

这个测试让替身返回 (nil, err)。旧代码进了 if err != nil，打完日志就继续往下走。等它执行到 response.StatusCode 时，response 还是 nil，没有结构体可读，于是 panic。

在 err != nil 分支的日志后面加上 return api.RegisterResult{}, err。重新跑同一条命令。

检查点 测试通过。适配器把原错误交还给调用它的 HTTP handler。真实请求中，handler 可以由此走到现有的 502 分支。

nil 响应保护 

1

"$s04_go" test -tags stdjson -count=1 ./internal/user_rpc -run '^TestRegisterReportsMissingResponse$'

这次替身返回 (nil, nil)，所以刚修好的 err 分支不会执行。旧条件 response != nil 又会跳过「响应缺失」分支，最后照样在 response.StatusCode 处 panic。

把条件改为 response == nil。在该分支的日志后返回 api.RegisterResult{}, errors.New("user rpc: missing register response")，并在 import 中加入标准库 "errors"。

gofmt -w internal/user_rpc/register.go
