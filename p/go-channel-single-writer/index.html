make(chan result) 创建了什么？ 

1

resultChannel := make(chan result)

创建一个传输 result 类型值的无缓冲 channel。

注意：

  • 它不是普通 slice。
  • 它不是已经存放结果的容器。
  • 它提供发送方与接收方之间的通信和同步。

发送：

1

resultChannel <- r

接收：

1

r := <-resultChannel

对于无缓冲 channel：

    |
    | 如果还没有接收方
    v
等待接收方
    |
    v
完成值传递
    |
    v
发送方继续

反方向也是一样：接收方会等待发送方提供值。

这里的阻塞是同步机制的一部分，不是程序出现了错误。

为什么恰好接收 len(urls) 次？

假设：

1

urls = [A, B, C]

函数启动三个 worker：

1
2
3

worker A -> 发送一个 result
worker B -> 发送一个 result
worker C -> 发送一个 result

接收循环：

1
2
3
4

for i := 0; i < len(urls); i++ {
	r := <-resultChannel
	results[r.url] = r.ok
}

执行三次接收：

1
2
3

第 1 次：收到 A 或 B 或 C 的结果
第 2 次：收到另一个结果
第 3 次：收到最后一个结果

顺序不固定，但每个 URL 都对应一个结果。

当第三次接收成功时，本次三个 worker 的发送操作都已完成，所有结果也已经被调用者写入 map。

之后再返回。

不需要猜测需要 Sleep 多长时间。

也不需要在这里关闭 channel：接收方已经知道要收多少个值，并且 channel 不会被继续使用。

注意边界：这个机制依赖每个 worker 都正常发送一次结果。如果发送次数不匹配，就可能永久阻塞。未来实际服务中还要考虑超时、取消和错误处理。

为什么 map 现在安全了？

看对象的访问关系：

1
2
3
4
5
6
7
8

worker A ─┐
worker B ─┼──> channel
worker C ─┘       |
                  v
          CheckWebsites 调用者
                  |
                  v
               results

worker 不再直接访问 results。

results 只由执行接收循环的 goroutine 修改。

channel 负责把不同 worker 的结果传递过去，并建立必要的同步关系。

因此不需要给这个 map 额外加锁。

这并不意味着 map 天然线程安全，而是我们通过设计消除了多个 goroutine 直接访问它的情况。
