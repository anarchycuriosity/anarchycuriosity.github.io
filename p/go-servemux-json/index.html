Go ServeMux｜路由复用与 JSON 响应断言

2026-10-20

为什么不继续写一堆 if？

上一篇已经暴露了问题：

PlayerServer 不应该在确认请求路径之前，就直接切割字符串。

最直接的修复是：

1
2

if path == "/league" ...
else if strings.HasPrefix(path, "/players/") ...

但随着端点数量增加，每次请求都需要自己判断路径、HTTP 方法、路径参数，以及没有匹配时如何回应。

Go 标准库已经提供了 http.ServeMux 来完成这件事。

新的请求路径：

ServeMux 的职责是选择处理者；业务 Handler 的职责是执行操作。

Handler 和 HandlerFunc 到底是什么关系？

先看接口：

http.Handler 要求实现 ServeHTTP(w, r)。

http.HandlerFunc 则是一个函数类型，它自己实现了 ServeHTTP，可以将符合签名的普通函数适配成 Handler。

因此：

       │
       ▼
http.HandlerFunc(...)
       │
       ▼
满足 http.Handler 接口
       │
       ▼
router.Handle(...)

ServeMux 自身同样实现了 http.Handler。

所以最终可以调用 router.ServeHTTP(w, r)，让路由器继续分发请求。

Go 1.22：不要再手动截取路径参数

原章使用旧写法：

"/players/" 匹配路径前缀，然后自己切片。

但 Go 1.22 已经支持：

  • GET /players/{name}：匹配 GET（也匹配 HEAD）。
  • POST /players/{name}：匹配 POST。
  • r.PathValue("name")：获取匹配的路径参数。

其中 {name} 匹配一个非空路径段，而不是任意长度的剩余路径。

例如：

请求 预期结果
GET /players/Alice 匹配 GET 玩家 Handler
POST /players/Alice 匹配 POST 玩家 Handler
DELETE /players/Alice 405 Method Not Allowed
GET /players/Alice/history 404 Not Found
POST /league 405 Method Not Allowed

Go 1.22 的 ServeMux 会自动处理一些未匹配情况，无须业务代码专门写 switch。

更具体的路由优先级遵循“更具体的匹配优先”，不是注册顺序决定胜负。

为什么使用嵌入，而不是手写 ServeHTTP？

先设想一个普通字段：

router *http.ServeMux

那么 PlayerServer 可以通过一个显式的 ServeHTTP 方法，委托给 router.ServeHTTP。

这是完全合理的写法。

原章进一步尝试 Go 的嵌入：

PlayerServer 嵌入 http.Handler 接口。

对象关系变成：

1
2
3
4
5

PlayerServer
├── store: PlayerStore
└── Handler: http.Handler
       │
       └── 实际保存 *http.ServeMux

因为 http.Handler 有 ServeHTTP 方法，嵌入后，Go 的方法提升机制会使 *PlayerServer 拥有这个方法。

于是可以删除自己写的委托方法。

这里不是 Java 式的继承。

更准确地说：

结构体里有一个嵌入字段，Go 将这个字段的方法提升到外层类型的方法集中。

没有发生对象继承，也没有复制一份路由器。

当外部调用 server.ServeHTTP 时，最终执行的仍然是内部 ServeMux 的实现。

注意必须先给嵌入字段赋值。如果没有调用构造函数就直接使用未初始化的 PlayerServer，其嵌入的 Handler 仍可能是 nil。

为什么不直接嵌入 ServeMux？

假设嵌入具体的 http.ServeMux。

由于它有 Handle、HandleFunc 等公开方法，这些方法也会提升到外层。

调用者可能获得这样的能力：

1
2
3
4

PlayerServer
├── ServeHTTP()
├── Handle()
└── HandleFunc()

这意味着外部代码能修改服务器内部的路由配置。

但 PlayerServer 原本只想对外提供请求处理能力，不一定想提供路由配置能力。

嵌入 http.Handler 接口后，提升的方法只有 ServeHTTP。

需要注意：嵌入的接口字段本身依然可被赋值，因此这不是最严格的封装。若必须禁止外部替换内部 Handler，可以保留私有字段并显式实现 ServeHTTP。

设计取舍：嵌入可以减少委托代码，但要清楚它会暴露什么 API。

同样地，Go 的接口也可以嵌入其它接口。例如 Animal 可以通过嵌入 Eater 和 Sleeper，组合两组方法要求。

为什么不直接比较 JSON 字符串？

考虑下面两段 JSON：

1

{"Name":"Chris","Wins":20}

1
2
3
4

{
  "Wins": 20,
  "Name": "Chris"
}

它们的空格、换行和字段顺序不同，但表示相同的数据。

如果测试直接比较字符串，就可能因为无关紧要的格式改变而失败。

更好的测试方法：

  1. 发起请求。
  2. 将响应 JSON 解码为 []Player。
  3. 比较解码后的 Go 数据。

这也让失败信息更贴近业务数据，而不是一大段难以阅读的 JSON 字符串。

不过有一个边界：[]Player 是切片，reflect.DeepEqual 会比较元素顺序。如果 API 不承诺联盟列表的排列顺序，测试也不应该假定顺序固定。

本篇只有一个玩家，因此不会出现顺序问题。

Encoder 和 Decoder 为什么接收 Reader/Writer？

json.NewEncoder(w) 需要的是 io.Writer。

http.ResponseWriter 实现了 io.Writer，因此 JSON 编码器可以把编码后的字节写进 HTTP 响应。

json.NewDecoder(response.Body) 需要的是 io.Reader。

测试里的 response.Body 是 *bytes.Buffer，它实现了 io.Reader，所以可以直接读取其中的响应正文。

这正是接口带来的好处：

JSON 编解码器不需要知道数据来自 HTTP、文件，还是内存缓冲区。

调用 Decode(&got) 时传入指针，是为了让解码器修改 got 中保存的数据。

没有地址，解码器就不能把解析出来的结果写回调用者的变量。

此外，Go 的 JSON 编码器只会编码可导出的结构体字段。Name、Wins 首字母大写，因此能被编码；如果写成 name、wins，在默认配置下就不能作为结构体的公开 JSON 字段输出。

本章沿用原章的 "Name"、"Wins" 字段名。以后可以用 json 字段标签改变编码名称。
