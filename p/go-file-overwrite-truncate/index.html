Go 文件写入｜Seek、Truncate 与短写

2026-10-20
阅读时长: 2 分钟
... 次阅读

先预测一个故障

假设文件原有五个字节：

1

1 2 3 4 5

执行 Seek(0, io.SeekStart)，然后写入 "abc"。

文件会变成什么？

答案不是 abc，而是：

1

a b c 4 5

因为 Seek 只改变文件当前位置，Write 只覆盖被写入的字节，并不会自动缩短文件长度。

对于 JSON 来说，这可能留下非法尾部数据。

如何证明这个故障？

先写一个测试：

1
2
3
4

原文件：12345
写入：  abc
预期：  abc
实际：  abc45

如果去掉下面实现中的 Truncate(0)，测试就应该失败。

因此修复过程是：

1
2
3

Truncate(0) → 文件长度变成 0
Seek(0)     → 位置回到开头
Write(abc)  → 文件内容为 abc

为什么单独定义 tape？

RecordWin 不应每次自己关心 Seek、Truncate。

我们封装一个 tape：

1
2
3
4
5
6
7

JSON Encoder
     ↓
tape.Write
     ↓
Truncate + Seek + Write
     ↓
文件

tape 的 Write 语义是：用本次写入替换整份文件。

它不是通用的追加式 Writer。如果一个调用者分多次 Write 发送同一份文档，后一次会覆盖前一次。本例的 json.Encoder.Encode 将一次编码结果交给 Writer，适用于这个简化封装。

为了测试短写错误，这里使用一个私有的最小接口描述 Write、Seek、Truncate。原书后期直接使用 *os.File，也是合理选择。

为什么测试私有类型？

因为 abc45 是写入边界上的故障，单独测试它比依靠业务测试偶然碰到更直接。测试成本与抽象成本之间没有绝对规则。

什么是短写？

Write(p) 返回：

n, err

假设要求写 10 字节，但实现只写了 7 字节，同时返回 err == nil。

完整写入并没有成功。

tape 必须识别：

n != len(p)

然后返回 io.ErrShortWrite。

否则调用者可能误认为数据已经完整保存。
