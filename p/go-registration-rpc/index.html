Go Kitex 注册服务｜跨进程调用与 RPC 错误映射

2026-11-22
阅读时长: 5 分钟
... 次阅读

同一个注册请求，为什么停掉 user 就变了？

整篇只追这一条请求：

1

POST /douyin/user/register/?username=alice&password=p

在 S03 的 show 里，user 在线时，这条请求得到 HTTP 200，响应中有 status_code: -1 和「账号持久化尚未接入」。只停 user，保留 API，再发同一条请求，HTTP 变成 502。与此同时，API 自己的 /healthz 仍可返回 200。

这个现象把问题缩到一处。API 进程明明还活着，注册 handler 又要去哪里找答案？ S02 已经把 alice 和 p 读出来并做了校验，接下来会调用 register(ctx, username, password)。S03 就是在启动 API 时给这个 register 接上真实的 RPC 调用。你自己的 learner 即使注册替身测试已经通过，总路由和真实进程入口仍要接好才能观察到这个现象。 S02 保留的 handler · API 自己的健康路由

启动时，main 给 handler 的是什么？

先看 cmd/api/main.go。它读用户服务地址，默认是 127.0.0.1:8881，然后调用 user_rpc.NewClient。返回的 *user_rpc.Client 持有一个由 userservice.NewClient 创建的 Kitex 客户端。前者是我们写的适配对象，后者负责发起 RPC。

下一行关键代码是 api.NewServer(address, user_client.Register)。读这里时留意 Register 后面没有括号。Go 会取出绑定在这一个 user_client 上的方法值，把它当函数传下去。你可以把它读成「收到合法注册请求时，就用这个客户端对象执行 Register」。真正调用的括号在 S02 handler 的 register(ctx, username, password) 上。

所以 API 启动时已经知道将来用谁调用，只有请求来了才知道这次要传什么。创建客户端成功也只说明对象准备好了。能否连到 8881，要等实际调用才知道。 API 启动与方法值 · 适配对象和 NewClient

要找的角色 代码里看哪里 什么时候出现
API 的注册适配对象 cmd/api/main.go 的 user_client 启动时创建，后续多次请求共用
适配对象里的 Kitex 客户端 internal/user_rpc/register.go 的 c.user_client 创建适配对象时存进去，发 RPC 时使用
这一次注册请求 (*Client).Register 里的 request alice 通过 HTTP 校验后才创建
远端业务实现 cmd/user/main.go 的 handler user 启动时登记，收到 RPC 时才执行它的方法

停靠点。 在 main 里找到传方法值的位置，再到 handler 里找到有括号的那一次调用。假如 user 此刻没启动，API 仍可以先建立自己的监听。等第一个合法 POST 进来，连接问题才会出现在调用结果里。

user 收到请求以后，怎样找到我们的业务方法？

换到 user 进程。它的 main 创建 &user_service.UserServiceImpl{}，把这个实例登记给生成的 userservice.NewServer，随后才开始监听。收到 Register 调用时，生成代码里的 registerHandler 取出解码好的请求，调用登记对象的 Register 方法。

这就是为什么 UserServiceImpl 可以是空结构体。这一步框架需要的是它提供的 Register 方法。 当前没有数据库连接等状态要保存在实现对象里。& 取出实例的指针，传给框架的是这个指针。

看 internal/user_service/register.go 里的两次取值。request.GetUsername() 和 request.GetPassword() 来自 protobuf 生成代码，接收者为空时也会返回空字符串。业务方法再判断是否缺参或超过 32 字节。这次校验保护的是 RPC 入口，直接调 user 的其他调用方也会经过。alice 和 p 通过后，方法返回一份业务答复「账号持久化尚未接入」，第二个返回值为 nil。 user 进程启动 · 生成的服务端分发 · 生成的 getter · 业务方法

动手。 先按固定源码写 internal/user_service/register.go，把该文件的项目内 import 改成 learner 的 module 前缀。再写 cmd/user/main.go，参考附录。先用两个输入预测这个方法的行为。只有 alice 时会在 RPC 校验处得到「用户名或密码不符合要求」。给齐 alice 和 p 时，会继续到「账号持久化尚未接入」。

ctx 在哪里交接？ API 进程内，handler 把自己的 ctx 传给适配方法，适配方法再交给 Kitex 客户端。远端 handler 收到的是服务端框架提供的 context，两端各有自己的对象。本步把连接超时设为 500ms，RPC 超时设为 2s。客户端超时只说明它结束了这次等待，远端可能已经处理过请求，所以注册暂不自动重试。show 的超时测试里，客户端返回后，服务端仍要等测试主动释放。至于浏览器关闭时远端是否停工，从这条链推不出来。 show 的超时测试

结果回来以后，谁选 200，谁选 502？

用同一个 alice 和 p 对照每一次交接：

调用的一方 → 接手的一方 这次交过去什么 返回后谁解释
HTTP handler → (*Client).Register ctx、alice、p handler 检查 error，然后决定 HTTP 状态和 JSON
手写适配方法 → Kitex 客户端 本次 UserRegisterRequest 适配方法检查调用错误和空响应，有响应时转成 api.RegisterResult
registerHandler → UserServiceImpl.Register 服务端 context 与解码后的请求 user 决定业务答复，框架把它带回 API

user 在线时，RPC 返回「账号持久化尚未接入」和 nil 错误。适配器把业务码 -1 原样交还，Hertz 写 HTTP 200。停掉 user 时，适配器拿到调用错误，Hertz 走 S02 已有的 502 分支。用户服务解释业务，HTTP handler 解释怎样回 HTTP。 适配方法的返回分支 · HTTP 状态选择

动手。 保留 learner 的 S02 internal/api/register.go。在已有的 server.go 里沿 NewServer → RegisterRoutes → RegisterUserRoute 传下 register，然后补 cmd/api/main.go。现有测试里调用 RegisterRoutes(hz) 的位置要跟着新签名调整。健康路由测试可以传 RegisterRoutes(hz, nil)，直接登记注册路由的替身测试可以保留现有调用方式。 show 的总路由接线 · show 的测试调用点

预测一下。 如果总路由少了 RegisterUserRoute(hz, register)，同一个 POST 会在 Hertz 得到 404，独立登记路由的替身测试仍可能通过。如果路由接好了，但参数仍是 nil，合法请求会走 503。只有函数接好、实际调用失败时，才会看到这里要验证的 502。
